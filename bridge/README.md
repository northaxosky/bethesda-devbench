# DevBench external bridge

The restart-surviving stdio MCP companion and ownership-safe MO2 session
controller. Game profiles and offline schemas are generated by the native
framework, rather than maintained as a separate bridge registry.

The bridge:

- keeps one MCP stdio process alive while the selected game stops and restarts;
- starts successfully when no game or `runtime.json` exists;
- always exposes the local `devbench.session` tool;
- exposes the selected game's core-tool catalog while offline, without claiming the
  game is ready, and replaces it with live DLL discovery when connected;
- sends `notifications/tools/list_changed` on connection, disconnection,
  instance replacement, or descriptor changes;
- never includes consumer-added tools in its offline catalog;
- connects only to `http://127.0.0.1:<validated-port>`;
- verifies `pid`, `instanceId`, `exePath`, runtime, and DLL identity;
- sends `X-DevBench-Instance` on every health, discovery, event, and tool call;
- never retries a remote POST automatically.

State and protocol diagnostics go to stderr. Stdout is reserved for MCP framing,
except for the explicit `setup` and `--help` commands.

## Commands

```powershell
npm ci
npm run validate
node dist/index.js --game fo4
node dist/index.js --game se
node dist/index.js --game vr
node dist/index.js setup --game fo4
```

| Game ID | Executable | Extender | Aliases |
|---|---|---|---|
| `fo4` | `Fallout4.exe` | F4SE | `fallout4` |
| `se` | `SkyrimSE.exe` | SKSE | `skyrimse`, `sse` |
| `vr` | `SkyrimVR.exe` | SKSE | `skyrimvr` |

Starfield is a source placeholder, not a supported bridge target.

Building the companion uses the repository's Windows C++/xmake toolchain to
generate `src\generated\core-tools.json` from the same descriptor factories as
the plugin. The `devbench-bridge` xmake target builds that dependency before
packaging. Offline calls still return an unavailable error; catalog presence
does not imply a game instance or provider is ready.

Discovery options:

```text
--game fo4
--install C:\Path\To\Fallout 4
--runtime-file C:\Path\To\runtime.json
--config C:\Path\To\session.json
```

`--install` constrains a responding identity to that folder's selected game executable.
The normal out-of-VFS candidate is
`%LOCALAPPDATA%\devbench\<game-id>\runtime.json`. An explicit runtime file is also
searched when provided, but cannot override the selected game. A legacy runtime file without `instanceId` is rejected
with an upgrade-required message rather than treated as a controllable host.

`setup` prints only the JSON MCP snippet; it never edits a client config.
Unknown options and missing option values are fatal.

## Session controller

The default machine config path is
`%LOCALAPPDATA%\devbench\<game-id>\session.json`. It is not created automatically.
The simple proxy remains available when the default file is absent. An explicit
invalid `--config` fails bridge startup. Copy `config.example.json` and replace
every placeholder with an absolute Windows path.

The config names the portable MO2 executable, actual profiles directory and profile,
MO2 shim executable label, game and script extender executables, physical deployed DLL, evidence
directory, and only the log paths that may be collected. A log entry with
`"crash": true` (a file, or a directory with `pattern`) is also a crash signal: a
matching file that appears or grows after the launch (or reclaim) fails a wait as `crashed`. The
optional `exitMarker` (`{"path", "match"}`, absolute path) names the log whose
newly appended line containing `match` (for example `[RootBuilder] Clear complete!`
in `mo_interface.log`) proves MO2 cleanup finished after a stop. It may pin the runtime
version and DLL SHA-256. The controller validates the profile directory and
deployed DLL before launch; it never edits `modlist.txt`, INIs, saves, or any
MO2/game setting.

### One-time MO2 launcher entry

Keep the configured MO2 instance open. The controller will not start, close,
or restart MO2; stopping a game waits for both the game and its native shim to exit.
Launch requests use MO2's single-instance pipe and remain connected until the
shim acknowledges them, avoiding early-disconnect races in CLI forwarding.

No elevation or system-wide process tracing is needed. Add an executable to
your portable MO2 instance with (Fallout 4 example):

- **Title:** `DevBench Launch` (matches `executable` in the session config).
- **Binary:** the physical packaged `platform\devbench-launch.exe`.
- **Arguments:** `-GameExe "C:\Path\To\Fallout 4\Fallout4.exe"`
- **Start in:** the Fallout 4 installation directory.

Keep all packaged `platform` files together. Use the physical packaged
paths, not the game's virtual Data directory. The helper validates this entry
in the adjacent `ModOrganizer.ini` before asking MO2 to run it. The config's
`loaderExe` points to the appropriate `f4se_loader.exe`, `skse64_loader.exe`,
or `sksevr_loader.exe` beside `gameExe`; RootBuilder may supply it only after
MO2 starts the shim.

PowerShell 7 runs only the external broker, outside MO2's VFS. MO2 launches
the native shim instead; the Store PowerShell host crashes under this MO2
installation's injection and must not be used as its executable entry.

The broker creates a current-user-only launch pipe. The MO2-launched native shim
authenticates that pending launch, starts the script extender inside MO2's VFS, retains the
loader handle, and transfers an actual game handle to the broker. The shim
waits for game exit so MO2/RootBuilder keeps its normal cleanup lifetime even
if the bridge disconnects. Starting the shim without a pending controller
launch fails without starting the script extender. Launcher failures are also
written to `%LOCALAPPDATA%\devbench\launch-shim.log`.

`devbench.session` actions. Every call blocks until the real event and returns its
result; nothing sleeps, polls, or needs REST. Long calls send MCP progress
notifications (when the request has a `progressToken`) and are cancellable.

- `status`: local controller/config/job/ownership status.
- `start`: launch a new game through the Windows helper, wait for the runtime
  identity (matching `runtime.json`, process creation, executable, loaded DLL
  path/hash, runtime version), then for `canLoad`. Returns the job result.
- `run`: start or reuse only the already-owned game, wait for `canLoad`, load the
  required named `fixture`, wait for `playerReady` of that `operationId`, run a
  server-side scenario with `async:true` until its `scenario.finished` event (then
  one `scenario status` read), collect evidence, then stop or release ownership.
  Returns the job result.
- `detach:true` on `start`/`run` returns `{queued, runId}` at once; `wait {runId}`
  then blocks until that job finishes and returns `status`.
- `wait {until}`: block on one condition against the owned game (requires a
  started game; use the proxied `await` argument otherwise):
  `canLoad`, `playerReady {operationId?, actionCursor?}`, `menu {name, open?}`,
  `event {topic, match?, after?}`, `frames {count}`. Returns a wait result.
  `canLoad` also waits for the engine's own load gate (`Main::GetCanLoad`), which
  plugins such as Community Shaders hold while compiling shaders.
- `stop`: request a graceful close, then wait for the game to exit, the launch shim
  to exit (`release` is refused until it has), and, when `exitMarker` is
  configured, for a line containing `exitMarker.match` appended after this launch.
  Returns `{ok, exited, forced, shimExited, exitMarker: {matched, line}|null, crash?}`.
  `force:true` terminates the game when the stop ceiling passes, including after an
  uncertain mutation. A stop that did not finish keeps ownership. Without a
  retained game, `stop` reclaims one an earlier bridge launched and never released
  (recorded under `%LOCALAPPDATA%\devbench\owned\`); its marker offset is taken at
  stop time.
- `cancel`: cooperative cancellation of the active controller job. Cancelling the
  MCP request of a blocking `start`/`run` does the same; cancelling a `wait` or
  `stop` call only ends that call.

Example run call:

```json
{
  "action": "run",
  "fixture": "DevBenchFixture01",
  "steps": [
    {
      "assert": {
        "tool": "inspect",
        "args": { "kind": "state" },
        "path": "/playerLoaded",
        "eq": true
      }
    }
  ],
  "finish": "stop",
  "forceStop": false
}
```

Exactly one of `steps` or `scenarioFile` is required. `finish` defaults to
`stop`; `leave-running` calls the helper's `release` operation, after which this
controller refuses to adopt or stop that process. If a mutation response is
lost or times out, the report says the outcome is uncertain, the mutation is
not retried, and the controller performs no further automatic writes or stop
until a `stop` with `force:true` ends the game.

### Waits and failure signals

A wait takes an event cursor, evaluates its condition once, then long-polls
`/api/await/events` and re-evaluates when a relevant event arrives. A state read
that returns HTTP 503/504 means "not yet" and is re-evaluated on the next event or
long-poll return. Results:

```json
{ "ok": true, "until": "playerReady", "satisfied": {}, "cursor": 412, "elapsedMs": 2310 }
{ "ok": false, "until": "playerReady", "reason": "loadFailed", "detail": {}, "cursor": 409, "elapsedMs": 640 }
```

Failures come from real signals; the ceiling is only a safety net.

| `reason` | Signal |
|---|---|
| `exited` | the owned game process exited (helper `gameExited`) |
| `crashed` | a `"crash": true` log file was created or grew since the game was launched or reclaimed, including between calls |
| `stalled` | `health.stalled` not resolved by `health.resumed` within `stallMs` while the game window is foreground; `detail` carries frame and pending tasks. A stall in the background is reported in progress, not failed |
| `modal` | a `MessageBoxMenu` opened during `canLoad`/`playerReady`; `detail.snapshot` holds its text and buttons (accept it with the `menu` tool, then wait again) |
| `loadFailed` | the correlated load operation failed or was cancelled, or `postLoadGame {success:false}` followed the action cursor |
| `operationFailed` | a correlated operation (such as `game save`) failed |
| `actionsDisabled` | native game actions are disabled in the plugin config |
| `eventHistoryLost` | the event ring dropped events the wait needed |
| `uncorrelated` | the receipt had no field to correlate a client `await` event against |
| `unavailable` | the listener went away, the instance changed, or the await endpoint is missing |
| `cancelled` | MCP request cancellation or `cancel` |
| `ceiling` | `ceilingMs` passed without any other signal |

Exit and crash-log signals exist only for a game this controller launched; waits on
a borrowed instance (proxied `await`) get `unavailable`, `stalled`, `cancelled`, and
`ceiling`.

### Proxied outcomes

Mutating proxied tools accept `await`, which the bridge strips before forwarding:

| `await` | Behavior |
|---|---|
| omitted / `true` | block on the known outcome and return `{...receipt, outcome}`: `game load` waits for `playerReady` of its `operationId`; `game save` for its operation to finish; `menu open`/`close` for that menu state; `scenario run` with `async:true` for `scenario.finished` of its `runId` |
| `false` | return the bare receipt |
| `{event, correlate}` | wait for `event` whose `data[correlate]` equals the receipt's `[correlate]` (for example `communityshaders_capture` with `{event:"communityshaders.capture.completed", correlate:"requestId"}`) |

The call is an error when `outcome.ok` is false. A failed wait never re-sends the
mutation. Without `after`, an `event` wait with `match` also scans events retained
from before the wait.

### Timings

`timings` in `session.json` is optional; absent keys keep these defaults
(positive integer milliseconds).

| Key | Default | Meaning |
|---|---|---|
| `stallMs` | 120000 | foreground main-thread stall before a wait fails |
| `ceilingMs` | 600000 | safety ceiling of every wait |
| `stopCeilingMs` | 120000 | safety ceiling of each stop stage (game exit, shim exit, exit marker) |

The launch handshake with MO2 has a fixed 60 s ceiling. The removed keys
`healthTimeoutMs`, `mainMenuTimeoutMs`, `loadTimeoutMs`, `scenarioTimeoutMs`,
`gracefulStopTimeoutMs`, `pollIntervalMs`, `platformStartTimeoutMs`, and
`mainThreadStallBudgetMs` fail validation with the replacement named.

In-scenario gates (`waitFor`, `waitUntil`) default to 10 s, steps and waits are
capped at 30 s, the host caps a whole scenario run at 60 s, and capture defaults
to 6 s. Synchronous `scenario` calls through the proxy get an HTTP transport
timeout of the 60 s run cap plus a 15 s margin (requested `timeoutMs` plus margin
for `capture` and `papyrus`); other calls keep 30 s. That is a transport bound,
not a flow wait.

## Evidence

Each job creates a unique folder under `resultsDir` and atomically writes
`result.json`. Reports distinguish `launchfailed`, `identitymismatch`,
`loadfailed`, `scenariofailed`, `cancelled`, `cleanupfailed`, and `complete`.
Failures add the wait's `reason` and `detail`. Reports include the controller run ID, remote instance ID, PID/creation time,
runtime, DLL SHA-256, source paths, expected/actual identity, transcript, and
cleanup result.

Configured logs are snapshotted before the job by size, mtime, file identity,
and a content prefix. Only files created, replaced, truncated, or changed during that job
are copied, up to the configured per-file bound. Larger captures remain
referenced by source path; bounded text captures are marked truncated. Dumps, PDBs, and arbitrary
directories are not copied. No automatic retention or recursive root deletion
is performed.

## Packaging

- Node entry: `dist/index.js`
- Node helper: `dist/platform/windows-session.ps1`
- Broker implementation: `dist/platform/LaunchShim.cs`
- Native launcher: `dist/platform/devbench-launch.exe`
- Standalone entry after `npm run compile`:
  `standalone/devbench-bridge.exe`
- Standalone helper:
  `standalone/platform/windows-session.ps1`
- Standalone broker:
  `standalone/platform/LaunchShim.cs`
- Standalone launcher:
  `standalone/platform/devbench-launch.exe`

The helper is spawned attached with:

```text
<absolute-path-to-pwsh.exe> -NoProfile -NonInteractive -File <path>
```

The Node client resolves PowerShell 7's `pwsh.exe` to an absolute path from
`PATH` (including enabled Microsoft Store app-execution aliases) before the
standard `%ProgramFiles%\PowerShell\7` installation. Store aliases are checked
against their linked executable and launched through the alias. The client does
not fall back to Windows PowerShell 5.1 and never uses `-ExecutionPolicy Bypass`.

EOF and bridge shutdown release native handles/lease; they do not kill the game
or MO2. The standalone build uses the project-local Bun package only.

## Plugin contract required by the bridge

The plugin's mirrored and Data-relative `runtime.json` must contain:

```json
{
  "gameId": "fo4",
  "pid": 1234,
  "port": 8930,
  "instanceId": "1234-01DC000000000000",
  "exePath": "C:\\Path\\To\\Fallout 4\\Fallout4.exe",
  "runtime": "1.11.240.0",
  "dllPath": "C:\\Physical\\Path\\To\\devbench.dll"
}
```

`instanceId` is `<pid>-<16 uppercase hexadecimal FILETIME creation ticks>`.
`gameId`, when present, must agree with the executable and selected game.
`/api/health` must return the matching full identity. Before dispatching
`/api/*` and `/mcp*`, the plugin must reject empty, duplicate, or mismatched
`X-DevBench-Instance` headers with HTTP 409. The header remains optional for
direct clients, but the bridge always sends exactly one. The bridge assumes no
stronger authentication and must remain loopback only.

Waits also rely on `GET /api/await/events?since=N&waitMs=M` (returns `{headSeq,
oldestSeq, events}` at once when events after `N` exist, else holds up to
`M` ms), `GET /api/await/frame?after=F&waitMs=M` (`{frame, advanced}`), the
`lifecycle`, `menu`, `health.stalled`/`health.resumed`, and `scenario.*` event
topics, and `foreground` in `inspect {kind:"health"}`. `runtime.json` is watched
with `fs.watch`; because it is written right after the listener thread starts, a
refused first connection is retried briefly (about 1 s) per file change.

Proxy/controller tests use fake HTTP servers and injected platforms. Native
tests use synthetic MO2/loader/game processes, including forwarding through an
existing launcher, rapid loader exit, ownership transfer, and bridge EOF.
They do not launch real games or MO2. Real MO2 forwarding, RootBuilder behavior,
game window close, and the complete game session still require supervised
runtime validation on the configured profile.
